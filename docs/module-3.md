## 1. Templates with Jinja2

### The template module

The `template` module renders a Jinja2 file and copies the result to the target.

```yaml title="playbooks/04_templates.yml (excerpt)"
- name: Deploy a config file
  hosts: servers
  gather_facts: false

  tasks:
    - name: Render the config template
      ansible.builtin.template:
        src: myconfig.conf.j2
        dest: /tmp/myconfig.conf
        mode: "0644"
```

### Jinja2 basics

Create a template file `playbooks/templates/myconfig.conf.j2`:

```jinja title="playbooks/templates/myconfig.conf.j2"
# Configuration for {{ inventory_hostname }}
# Generated by Ansible

hostname {{ ansible_hostname }}
domain_name {{ ansible_domain | default('example.com') }}
timezone {{ ansible_date_time.timezone | default('UTC') }}

# Network settings
{% for iface in ansible_interfaces %}
interface {{ iface }}
{% endfor %}

# This host has {{ ansible_processor_vcpus | default('unknown') }} CPU(s)
```

### Jinja2 filters

Filters transform variable values. Common ones:

| Filter | Example | Result |
|--------|---------|--------|
| `default` | `{{ var \| default('fallback') }}` | Uses 'fallback' if var is undefined |
| `upper` | `{{ hostname \| upper }}` | UPPERCASE |
| `lower` | `{{ hostname \| lower }}` | lowercase |
| `to_json` | `{{ data \| to_json }}` | JSON string |
| `to_yaml` | `{{ data \| to_yaml }}` | YAML string |
| `bool` | `{{ "yes" \| bool }}` | true |
| `ternary` | `{{ enabled \| ternary('on', 'off') }}` | 'on' or 'off' |

### Exercise: Template a simple web page

1. Create `playbooks/templates/index.html.j2`:

```jinja title="playbooks/templates/index.html.j2"
<!DOCTYPE html>
<html>
<head>
    <title>{{ page_title | default('Ansible Workshop') }}</title>
</head>
<body>
    <h1>Welcome to {{ ansible_hostname }}</h1>
    <p>Managed by Ansible</p>
    <p>OS: {{ ansible_distribution }} {{ ansible_distribution_version }}</p>
    <p>Uptime: {{ ansible_uptime_seconds | default('unknown') }} seconds</p>
    <hr>
    {% for service in services %}
    <p>Service: {{ service.name }} - {{ service.status }}</p>
    {% endfor %}
</body>
</html>
```

2. Create a playbook `playbooks/04_templates.yml`:

```yaml title="playbooks/04_templates.yml"
- name: Deploy a dynamic web page
  hosts: servers
  gather_facts: true

  vars:
    page_title: "My Workshop Page"
    services:
      - { name: ssh, status: running }
      - { name: nginx, status: stopped }

  tasks:
    - name: Create the web directory
      ansible.builtin.file:
        path: /var/www/html
        state: directory
        mode: "0755"

    - name: Deploy the index page
      ansible.builtin.template:
        src: index.html.j2
        dest: /var/www/html/index.html
        mode: "0644"

    - name: Show the rendered file
      ansible.builtin.command: cat /var/www/html/index.html
      register: page_content

    - name: Display the page
      ansible.builtin.debug:
        var: page_content.stdout_lines
```

3. Run it:

```bash
ansible-playbook playbooks/04_templates.yml
```

## 2. Roles

### What is a role?

A role is a structured way to organize playbooks, variables, templates, and handlers. It promotes reusability.

### Role directory structure

```
roles/my_role/
├── tasks/
│   └── main.yml        # Main task list
├── vars/
│   └── main.yml        # Variables
├── templates/          # Template files
├── handlers/
│   └── main.yml        # Handlers
├── defaults/
│   └── main.yml        # Default variables (lowest precedence)
└── files/              # Static files to copy
```

### Creating a role

Use the `ansible-galaxy` command:

```bash
ansible-galaxy init roles/web_server
```

This creates the directory structure above.

### Using a role in a playbook

```yaml title="playbooks/05_roles.yml"
- name: Configure web servers using a role
  hosts: servers
  gather_facts: true

  roles:
    - web_server
```

### Exercise: Refactor a playbook into a role

1. Start with this flat playbook:

```yaml title="playbooks/05_roles_flat.yml (starting point)"
- name: Configure web server (flat)
  hosts: servers
  gather_facts: false

  vars:
    web_port: 80
    document_root: /var/www/html

  tasks:
    - name: Create document root
      ansible.builtin.file:
        path: "{{ document_root }}"
        state: directory
        mode: "0755"

    - name: Deploy index page
      ansible.builtin.template:
        src: index.html.j2
        dest: "{{ document_root }}/index.html"
        mode: "0644"

    - name: Ensure nginx is installed
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Ensure nginx is running
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

2. Refactor into a role at `roles/web_server/`:

   - `roles/web_server/tasks/main.yml` — move tasks here
   - `roles/web_server/defaults/main.yml` — move variables here as defaults
   - `roles/web_server/templates/index.html.j2` — move template here

3. Create the role:

```bash
ansible-galaxy init roles/web_server
```

4. Move the files:

```bash
# Create task file
cat > roles/web_server/tasks/main.yml << 'EOF'
- name: Create document root
  ansible.builtin.file:
    path: "{{ document_root }}"
    state: directory
    mode: "0755"

- name: Deploy index page
  ansible.builtin.template:
    src: index.html.j2
    dest: "{{ document_root }}/index.html"
    mode: "0644"

- name: Ensure nginx is installed
  ansible.builtin.package:
    name: nginx
    state: present

- name: Ensure nginx is running
  ansible.builtin.service:
    name: nginx
    state: started
    enabled: true
EOF

# Create defaults
cat > roles/web_server/defaults/main.yml << 'EOF'
document_root: /var/www/html
web_port: 80
EOF

# Move template (already exists from Module 3)
cp playbooks/templates/index.html.j2 roles/web_server/templates/
```

5. Create the role-based playbook `playbooks/05_roles.yml`:

```yaml title="playbooks/05_roles.yml"
- name: Configure web servers using a role
  hosts: servers
  gather_facts: true

  roles:
    - web_server
```

6. Run it:

```bash
ansible-playbook playbooks/05_roles.yml --check
```

### When to use a role

Use a role when:
- You want to reuse the same configuration across multiple playbooks
- The configuration has multiple tasks, variables, and templates
- You want to share it with others (via Ansible Galaxy)

Keep it simple: a flat playbook is fine for one-off tasks.

## 3. Import vs Include Tasks

Sometimes you want to split your task list across multiple files. Ansible gives you two ways to do this — and they behave very differently.

### `import_tasks` — Static (parse time)

`import_tasks` copies the tasks into your playbook **before it even runs**. The file is read at parse time, so:

- Imported tasks appear in the playbook as if they were written inline
- You **cannot** use variables set by previous tasks (they don't exist yet at parse time)
- The file path must be a literal string — no variable interpolation
- All tasks are registered as one continuous block

```yaml title="playbooks/06_import_tasks.yml (import_tasks example)"
- name: Static import
  hosts: servers
  gather_facts: false

  tasks:
    - name: Print a variable
      ansible.builtin.debug:
        msg: "Before import, my_var is {{ my_var }}"

    - name: Import tasks (static — happens at parse time)
      ansible.builtin.import_tasks:
        file: tasks_setup.yml
```

If `my_var` is not defined before the import, the imported tasks **cannot** use it — even if you define it between the import and where it's used. That's because the entire file was pulled in before anything ran.

### `include_tasks` — Dynamic (runtime)

`include_tasks` loads the file **when Ansible reaches that line** during execution. This means:

- Included tasks see all variables set by previous tasks
- You can use a variable for the file path (e.g., `include_tasks: "{{ my_file }}"`)
- Each `include_tasks` call is independent — you can include different files conditionally
- The included tasks run in place, preserving task numbering and handlers

```yaml title="playbooks/06_import_tasks.yml (include_tasks example)"
- name: Dynamic include
  hosts: servers
  gather_facts: false

  tasks:
    - name: Set a variable at runtime
      ansible.builtin.set_fact:
        setup_type: production

    - name: Include tasks (dynamic — happens at runtime)
      ansible.builtin.include_tasks:
        file: "setup_{{ setup_type }}.yml"
```

Here, `setup_type` is set by a previous task, and the included file can use it freely.

### Side-by-side comparison

| | `import_tasks` | `include_tasks` |
|---|---|---|
| **When loaded** | Parse time (before play starts) | Runtime (when reached) |
| **Can use task-set variables?** | No | Yes |
| **Variable file path?** | No (literal only) | Yes |
| **Good for** | Fixed task groups, shared utility tasks | Conditional logic, dynamic file selection |
| **Handlers notified** | Yes, but only once per play | Yes, independently per include |

### When to use which

- Use `import_tasks` when you have a **fixed** set of tasks that don't depend on runtime state — e.g., a standard "install prerequisites" block.
- Use `include_tasks` when you need **conditional** logic — e.g., include different setup files based on OS, or loop over a list of config files to process.

### Exercise: See the difference yourself

Create these three files:

**`playbooks/tasks_setup.yml`:**
```yaml
- name: Setup task from imported file
  ansible.builtin.debug:
    msg: "This is a setup step — my_var is '{{ my_var }}'"
```

**`playbooks/06_import_tasks.yml`:**
```yaml
- name: Import vs Include demonstration
  hosts: servers
  gather_facts: false

  tasks:
    # --- Static import (won't see my_var) ---
    - name: Define my_var
      ansible.builtin.set_fact:
        my_var: "hello from set_fact"

    - name: Try static import (my_var not available)
      ansible.builtin.import_tasks:
        file: tasks_setup.yml
      # This will show my_var as empty because import_tasks
      # was resolved at parse time, before set_fact ran.

    # --- Dynamic include (will see my_var) ---
    - name: Include tasks dynamically (my_var is available)
      ansible.builtin.include_tasks:
        file: tasks_setup.yml
      # This will show my_var = "hello from set_fact"
      # because include_tasks runs at runtime.
```

Run it:

```bash
ansible-playbook playbooks/06_import_tasks.yml
```

You'll see the first debug (from `import_tasks`) shows an empty `my_var`, while the second debug (from `include_tasks`) shows the value set by `set_fact`.
